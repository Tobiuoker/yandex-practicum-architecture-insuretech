# InsureTech - обоснование технологической архитектуры to-be

**Цели:** доступность ≥ 99,9%, RTO ≤ 45 мин, RPO ≤ 15 мин, рост нагрузки и работа 24/7 по РФ.

| Решение | Почему выбрано |
|---|---|
| **Один Kubernetes-кластер в 3 зонах доступности** | При отказе одной зоны сервис остается доступным в остальных. Один кластер проще сопровождать, чем три независимых. **Кластер один, зон - три.** |
| **Горизонтальное масштабирование** | Автоматически добавляем поды и узлы при росте нагрузки. Вертикальное масштабирование ограничено размером одной машины и не решает отказоустойчивость. |
| **Application Load Balancer: active-active между AZ** | Равномерно распределяет запросы. Health check исключает недоступную зону из маршрутизации; клиент продолжает работать по тому же адресу |
| **Cloud CDN + Object Storage** | Статика отдается из ближайших к пользователю узлов CDN, уменьшая различия во времени загрузки между регионами РФ. |
| **PostgreSQL: primary + 2 реплики в разных AZ** | Синхронная quorum-репликация (1 из 2), автоматическое переключение primary и единая точка подключения для записи снижают риск потери данных и простоя. |
| **Ежедневные бэкапы** | Можно восстановить БД на нужный момент, в том числе после логической ошибки. Реплики не заменяют резервные копии. |
| **Без шардирования БД** | При объеме 50 GB шардирование пока избыточно: усложнит запросы и сопровождение без очевидной пользы. |
| **Мониторинг 24/7** | Позволяет выявлять сбои сразу, а не после обращений пользователей. |
