# Задание 3. Проблемы и решение (Event-Driven)

| Проблема / риск | Решение |
|---|---|
| Рост числа страховых с 5 до 10 увеличивает задержки и ошибки синхронного агрегатора. | Отдельная очередь задач/воркер на каждую страховую; опрос раз в 15 минут, таймауты, ретраи и лимит параллелизма. Сбой одной компании не блокирует остальные. |
| Перегруз API агрегатора: `core-app` каждые 15 минут, а `ins-comp-settlement` раз в сутки запрашивают весь каталог по REST. | Агрегатор сравнивает данные со своей БД и отправляет **только изменения** в Kafka (`products.updated`). Оба сервиса подписаны на топик и обновляют локальные копии. |
| Суточная REST-выгрузка всех оформленных страховок из `core-app` создает пиковую нагрузку и риск неполной передачи. | `core-app` публикует `policies.created` **при каждом оформлении**. `ins-comp-settlement` сохраняет события и формирует реестр из своей БД раз в сутки. |
| При сбое между записью в БД и публикацией в Kafka возможна потеря событий; при повторной доставке - дубли. | **Transactional Outbox** в агрегаторе и `core-app`: данные и событие записываются одной транзакцией; воркер публикует в Kafka. Потребители делают дедупликацию по `event_id`; ошибки - retry/DLQ. |
| При недоступности внешних API данные могут устаревать. | Агрегатор хранит версии продуктов и время обновления; потребители продолжают использовать последнюю полученную версию с контролем ее актуальности. |

**Что остается REST:** работа с `client-info`, персональные расчеты/предложения по ОСАГО и обращения агрегатора к API страховых компаний. Декомпозиция сервисов не меняется.

**Топики:** `products.updated` (ключ `insurer_id + product_id`, изменение/деактивация) и `policies.created` (ключ `policy_id`). Отдельный топик на страховую не нужен.
